App Gestión Dormitorios HVU-ULV

Proyecto Final - Arquitectura y Calidad de Software

Versión 1.0 – 2025

1. Introducción

1.1 Propósito

El presente documento define el Plan de Gestión de Configuración para la aplicación Gestión Dormitorios HVU-ULV, una solución móvil desarrollada en Flutter para Android e iOS, con un backend en Node.js/Express y una base de datos en SQL Server.

El objetivo de este plan es establecer los procesos, responsabilidades, herramientas y convenciones que se utilizarán para administrar los elementos de configuración del software, incluyendo:

  • Código fuente de la aplicación móvil (Flutter: Android / iOS).
  • Código fuente del backend (Node.js/Express).
  • Scripts y estructura de la base de datos (SQL Server).
  • Artefactos de documentación (SRS, arquitectura, pruebas, manuales, etc.).
  • Archivos de configuración de entornos y despliegue.

Este plan busca asegurar que todas las versiones, cambios y entornos del sistema se gestionen de manera controlada, trazable y coherente a lo largo del ciclo de vida del proyecto.

1.2 Alcance

El Plan de Gestión de Configuración aplica a todos los artefactos de software y documentación relacionados con la App Gestión Dormitorios HVU-ULV, incluyendo:

  • Repositorio del frontend Flutter (Android e iOS).
  • Repositorio del backend Node.js/Express.
  • Scripts y esquemas de base de datos SQL Server.
  • Documentos de análisis, diseño, pruebas y manuales.
  • Archivos de configuración para entornos de desarrollo, pruebas y producción.

El plan se aplicará durante todo el ciclo de vida del proyecto, desde el desarrollo inicial, pasando por las pruebas y entrega del proyecto final, hasta los posibles mantenimientos posteriores que se realicen en el contexto académico.

2. Contexto del Proyecto

La App Gestión Dormitorios HVU-ULV es una solución que permite administrar procesos clave del Hogar de Varones Universitarios, tales como:

  • Registro de asistencia mediante códigos QR a cultos y actividades.
  • Evaluaciones de limpieza por cuarto y pasillo.
  • Gestión de reportes disciplinarios y amonestaciones.
  • Asignación y administración de monitores.
  • Consultas administrativas para estudiantes, monitores y preceptor.

La solución se compone de:

  • Una aplicación móvil multiplataforma desarrollada en Flutter (Android e iOS).
  • Una API REST desarrollada en Node.js/Express.
  • Una base de datos centralizada en SQL Server.

Dado que se trata de un proyecto final académico, pero con una arquitectura cercana a un entorno real, es indispensable gestionar la configuración del sistema con disciplina, para evitar inconsistencias entre versiones de código, documentos, scripts y entornos.

4.2 Identificación y Nomenclatura de Elementos

Para garantizar la trazabilidad, los elementos de configuración se identificarán mediante convenciones de nombres y estructuras de carpetas claras. Algunos ejemplos:

  • Repositorio frontend: hvu-app-frontend
  • Repositorio backend: hvu-app-backend
  • Carpeta de documentación: docs/ dentro de un repositorio agregado o en un repositorio separado.
  • Scripts BD: db/scripts/01_create_schema.sql, db/scripts/02_seed_catalogs.sql
  • Documentos: docs/01_SRS_HVU.pdf, docs/02_Arquitectura_HVU.pdf, docs/03_Plan_Pruebas_HVU.pdf, docs/04_Plan_Config_HVU.html

La identificación de versiones se realizará principalmente mediante etiquetas (tags) en Git, siguiendo un esquema de versionado definido en la sección 6 de este documento.

6. Control de Versiones

El control de versiones es fundamental para mantener la trazabilidad, integridad y coherencia del software durante su ciclo de vida. El proyecto utilizará Git con repositorios separados para frontend, backend y documentación.

6.1 Esquema de Versionado Semántico

El sistema usará el estándar Versionado Semántico (Semantic Versioning) con la convención: 

MAJOR.MINOR.PATCH
  • MAJOR: Cambios que rompen compatibilidad o introducen una arquitectura nueva.
  • MINOR: Nuevas funcionalidades sin romper compatibilidad.
  • PATCH: Correcciones de errores y mejoras pequeñas.

Ejemplos:

  • 1.0.0 — Primera versión estable del proyecto.
  • 1.1.0 — Agrega la funcionalidad de amonestaciones.
  • 1.1.2 — Corrección de errores menores en asistencia.

6.2 Convenciones de Nombres en Ramas Git

Las ramas se estructurarán de la siguiente manera:

Tipo de rama Formato Descripción
Principal main Contiene solo versiones estables etiquetadas. Protegida.
Desarrollo develop Integración de funcionalidades antes de fusiones a producción.
Funcionalidad feature/nombre-funcion Desarrollo de nuevas funciones.
Corrección fix/nombre-bug Correcciones específicas.
Documentación docs/nombre-doc Actualizaciones de manuales, SRS, arquitectura, pruebas.

6.3 Convención de Mensajes de Commit

Los commits deben ser claros y seguir este formato:

[tipo]: descripción breve
Tipos permitidos:
  • feat: nueva funcionalidad
  • fix: corrección de error
  • docs: documentación
  • style: estética (no afecta funcionalidad)
  • refactor: reestructuración sin cambio funcional
  • test: pruebas
  • config: archivos de configuración

Ejemplo:

feat: agregar pantalla de estadísticas para estudiantes

7. Procedimiento de Control de Cambios

Los cambios seguirán un flujo estructurado para garantizar calidad y trazabilidad:

7.1 Solicitud de Cambio (Issue)

Cualquier cambio debe registrarse como Issue en GitHub con la siguiente información:

  • Descripción del cambio o problema.
  • Archivo(s) o módulo(s) involucrados.
  • Impacto esperado en el sistema.
  • Responsable asignado.

7.2 Desarrollo del Cambio

El desarrollador:

  • Crea una rama feature/, fix/ o docs/.
  • Implementa el cambio.
  • Realiza commits siguiendo las convenciones.

7.3 Revisión (Pull Request)

Todos los cambios deben pasar por un Pull Request en GitHub. El responsable de configuración revisa:

  • Calidad del código.
  • Afectaciones a otros módulos.
  • Consistencia con arquitectura y requisitos.

7.4 Aprobación e Integración

Una vez aprobado el PR, se hace merge a la rama develop y, cuando sea una versión estable, se fusiona a main.

7.5 Documentación del Cambio

Todo cambio debe registrarse en un archivo CHANGELOG.md con el siguiente formato:

## [1.2.0] - 2025-11-20
### Agregado
- Nueva vista de reportes para preceptores.

### Corregido
- Error en el cálculo de calificación final de limpieza.

8. Gestión de Entornos

La aplicación cuenta con tres entornos principales:

Entorno Descripción Componentes involucrados
Desarrollo (DEV) Entorno donde los desarrolladores prueban nuevas funciones. Flutter, Node.js local, BD local o contenedor, variables .env.dev.
Pruebas (TEST) Entorno para pruebas integrales y pruebas del plan de QA. APK de pruebas, BD limpia, servidor de pruebas, .env.test.
Producción (PROD) Versión final estable entregada al profesor y usada en demostraciones. Build firmado Flutter, API estable, BD final, .env.prod.

8.1 Gestión de Variables de Entorno

Las variables sensibles no deben subirse al repositorio. Se manejarán plantillas:

  • .env.example (plantilla)
  • .env.dev
  • .env.test
  • .env.prod

8.2 Builds para Android e iOS

Flutter permite generar builds para ambos sistemas:

  • flutter build apk — Android
  • flutter build ios — iOS (desde macOS + Xcode)

Las versiones generadas deben almacenarse en:

/releases/android/ y /releases/ios/.

9. Auditorías de Configuración

9.1 Auditoría Funcional

Verifica que el sistema cumpla con los requisitos del SRS y arquitectura.

9.2 Auditoría Física

Verifica que la versión entregada contenga todos los artefactos definidos como EC.

9.3 Auditoría de Registros

Verifica que existan commits, PRs, issues, tags y changelogs completos.

10. Riesgos Asociados a la Configuración

  • Pérdida de sincronización entre frontend, backend y BD.
  • Eliminar o modificar código sin registrar un issue.
  • Hacer cambios directos en main.
  • No registrar versiones antes de pruebas o entregas.
  • Variables de entorno expuestas por error en el repositorio.

11. Estrategias de Mitigación

  • Activar protección de la rama main.
  • Usar Pull Requests obligatorios con revisión.
  • Documentar todo en el changelog.
  • Usar scripts versionados para BD.
  • No compartir variables .env por medios no seguros.
  • Etiquetar versiones antes de pruebas y entregas.

12. Conclusión

Este Plan de Gestión de Configuración garantiza que todo el ciclo de vida del proyecto se lleve a cabo con orden, trazabilidad y coherencia entre sus artefactos. La correcta aplicación del proceso permitirá que el software evolucione de manera controlada, asegurando versiones estables, reproducibles y alineadas con los requisitos y la arquitectura definida.
