App Gestión Dormitorios HVU-ULV

Proyecto Final - Arquitectura y Calidad de Software

Versión 1.0 – 2025

1. Introducción

1.1 Propósito

El presente documento define el Plan de Gestión de Configuración para la aplicación Gestión Dormitorios HVU-ULV, una solución móvil desarrollada en Flutter para Android e iOS, con un backend en Node.js/Express y una base de datos en SQL Server.

El objetivo de este plan es establecer los procesos, responsabilidades, herramientas y convenciones que se utilizarán para administrar los elementos de configuración del software, incluyendo:

  • Código fuente de la aplicación móvil (Flutter: Android / iOS).
  • Código fuente del backend (Node.js/Express).
  • Scripts y estructura de la base de datos (SQL Server).
  • Artefactos de documentación (SRS, arquitectura, pruebas, manuales, etc.).
  • Archivos de configuración de entornos y despliegue.

Este plan busca asegurar que todas las versiones, cambios y entornos del sistema se gestionen de manera controlada, trazable y coherente a lo largo del ciclo de vida del proyecto.

1.2 Alcance

El Plan de Gestión de Configuración aplica a todos los artefactos de software y documentación relacionados con la App Gestión Dormitorios HVU-ULV, incluyendo:

  • Repositorio del frontend Flutter (Android e iOS).
  • Repositorio del backend Node.js/Express.
  • Scripts y esquemas de base de datos SQL Server.
  • Documentos de análisis, diseño, pruebas y manuales.
  • Archivos de configuración para entornos de desarrollo, pruebas y producción.

El plan se aplicará durante todo el ciclo de vida del proyecto, desde el desarrollo inicial, pasando por las pruebas y entrega del proyecto final, hasta los posibles mantenimientos posteriores que se realicen en el contexto académico.

2. Contexto del Proyecto

La App Gestión Dormitorios HVU-ULV es una solución que permite administrar procesos clave del Hogar de Varones Universitarios, tales como:

  • Registro de asistencia mediante códigos QR a cultos y actividades.
  • Evaluaciones de limpieza por cuarto y pasillo.
  • Gestión de reportes disciplinarios y amonestaciones.
  • Asignación y administración de monitores.
  • Consultas administrativas para estudiantes, monitores y preceptor.

La solución se compone de:

  • Una aplicación móvil multiplataforma desarrollada en Flutter (Android e iOS).
  • Una API REST desarrollada en Node.js/Express.
  • Una base de datos centralizada en SQL Server.

Dado que se trata de un proyecto final académico, pero con una arquitectura cercana a un entorno real, es indispensable gestionar la configuración del sistema con disciplina, para evitar inconsistencias entre versiones de código, documentos, scripts y entornos.

3. Roles y Responsabilidades en la Gestión de Configuración

A continuación se describen los roles relacionados con la gestión de configuración del proyecto y sus responsabilidades.

Rol Responsabilidades principales en gestión de configuración
Responsable de Configuración (Líder de Configuración)
  • Definir y mantener este Plan de Gestión de Configuración.
  • Administrar los repositorios de GitHub (frontend y backend).
  • Aprobar la creación de ramas principales y reglas de protección.
  • Coordinar la numeración de versiones del sistema.
  • Supervisar los registros de cambios (changelogs).
Desarrolladores de Frontend
  • Trabajar en ramas de desarrollo/funcionalidad definidas.
  • Seguir las convenciones de nombres de commits y ramas.
  • Actualizar documentación técnica relacionada con la app móvil.
  • Notificar cambios relevantes al Responsable de Configuración.
Desarrolladores de Backend
  • Trabajar en ramas de servicios, endpoints y correcciones.
  • Mantener sincronizados los cambios de la API con la documentación.
  • Versionar scripts de base de datos y migraciones.
  • Informar cambios que impacten en otras capas (Flutter / BD).
Responsable de Base de Datos
  • Gestionar los scripts de creación y actualización de la BD.
  • Asegurar que los cambios en tablas, llaves y catálogos estén versionados.
  • Coordinar con backend las migraciones y ajustes de esquema.
Responsable de Pruebas / QA
  • Verificar que la versión probada corresponda a una etiqueta (tag) específica.
  • Registrar los resultados de pruebas asociados a versiones concretas.
  • Notificar defectos mediante issues en GitHub, referenciando commits o ramas.
Profesor / Revisor Académico
  • Revisar la consistencia entre artefactos (código, arquitectura, pruebas y documentación).
  • Validar que las versiones entregadas correspondan al alcance definido.

4. Elementos de Configuración (EC)

Los Elementos de Configuración (EC) son los artefactos que se gestionan explícitamente bajo control de configuración. Para la App Gestión Dormitorios HVU-ULV, se consideran EC los siguientes:

4.1 Clasificación de Elementos de Configuración

Categoría Ejemplos de EC
Código fuente – Frontend
  • Proyecto Flutter (Android e iOS).
  • Pantallas (screens) de login, dashboard, limpieza, reportes, asistencia, etc.
  • Widgets compartidos, providers, servicios HTTP.
  • Archivos de configuración pubspec.yaml, build.gradle, etc.
Código fuente – Backend
  • Proyecto Node.js/Express.
  • Rutas (/api/auth, /api/limpieza, /api/reportes, etc.).
  • Controladores, servicios y capa DAL.
  • Archivo de configuración .env (no se sube al repo, pero se maneja como plantilla).
Base de Datos
  • Scripts de creación de esquema en SQL Server.
  • Scripts de inserción de datos iniciales (catálogos).
  • Scripts de migración entre versiones de esquema.
Documentación
  • Especificación de requisitos (SRS).
  • Documento de arquitectura de software.
  • Plan de pruebas y documentación de resultados.
  • Manual de usuario y manual técnico.
  • Plan de gestión de configuración (este documento).
Configuración de entornos
  • Archivos de variables de entorno para desarrollo, pruebas y producción.
  • Configuración de conexión a la base de datos.
  • Archivos de configuración de despliegue (por ejemplo, scripts de publicación).

4.2 Identificación y Nomenclatura de Elementos

Para garantizar la trazabilidad, los elementos de configuración se identificarán mediante convenciones de nombres y estructuras de carpetas claras. Algunos ejemplos:

  • Repositorio frontend: hvu-app-frontend
  • Repositorio backend: hvu-app-backend
  • Carpeta de documentación: docs/ dentro de un repositorio agregado o en un repositorio separado.
  • Scripts BD: db/scripts/01_create_schema.sql, db/scripts/02_seed_catalogs.sql
  • Documentos: docs/01_SRS_HVU.pdf, docs/02_Arquitectura_HVU.pdf, docs/03_Plan_Pruebas_HVU.pdf, docs/04_Plan_Config_HVU.html

La identificación de versiones se realizará principalmente mediante etiquetas (tags) en Git, siguiendo un esquema de versionado definido en la sección 6 de este documento.

5. Herramientas de Gestión de Configuración

La gestión de configuración de la App Gestión Dormitorios HVU-ULV utilizará principalmente las siguientes herramientas:

Herramienta Uso principal
Git
  • Control de versiones distribuido para código y documentos.
  • Manejo de ramas, fusiones (merge) y etiquetas (tags).
  • Historial de cambios por archivo y por desarrollador.
GitHub
  • Alojamiento de los repositorios frontend, backend y documentación.
  • Gestión de issues para reportar defectos y tareas.
  • Pull requests para revisión de código antes de integrar cambios a ramas principales.
  • Protección de la rama main o master para evitar cambios directos.
GitHub Projects / Tablero Kanban (opcional)
  • Organización de tareas de desarrollo, pruebas y documentación.
  • Asignación de responsables y seguimiento del estado de cada tarea.
Entorno de Desarrollo (VS Code, Android Studio, Xcode)
  • Edición y compilación de la app Flutter para Android e iOS.
  • Desarrollo y depuración del backend Node.js.
  • Integración con Git para commits y manejo de ramas.
SQL Server Management Studio (SSMS)
  • Gestión de la base de datos, ejecución de scripts y verificación de estructura.
  • Exportación/importación de esquemas y datos iniciales.

El uso disciplinado de estas herramientas es obligatorio para todo cambio en el sistema. No se permitirá modificar directamente código en producción o en ramas protegidas sin seguir el flujo de trabajo establecido en este plan.
